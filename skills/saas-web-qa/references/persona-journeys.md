# Persona-based browser QA

Use this workflow when the user asks to experience a journey as different users, including a multi-agent or persona review. These are simulated perspectives, not actual people or representative user research. Honor the user's selected number, roles, target, and scope; otherwise use the ten roles below. A persona task does not itself authorize changes to application code or real-world side effects.

## Establish a shared starting point

- Identify the entry point, environment, account and workspace, account role, permitted actions, and the first observable success for each requested journey. For a public onboarding journey this might be reaching a usable dashboard; for a logged-in journey it is the requested in-product outcome, not merely successful login. Use the user's definition or infer one from the product; record the definition and any assumptions. If access or success is unclear and cannot be inferred, ask while continuing independent safe checks.
- When multiple journeys or core features are requested, list each in-scope journey with its entry point, account state, success criterion and assigned personas. Use the same entry and success criterion across personas assigned to the same journey unless the user explicitly requests otherwise. Track each journey's result separately; success in one does not establish success in the others. If the user requests broad coverage without naming features, inspect the product and select relevant journeys within the requested scope, stating which were covered and omitted.
- Match the starting state to each journey: use the public entry and login when that transition is in scope, or start from the designated authenticated landing page when only the internal product journey is requested. Where both are requested, continue after login to the in-product outcome when possible. If the login transition is blocked but an authorized session is already available, separately check the authenticated journey where permitted; report the public-to-authenticated path as blocked and do not claim an uninterrupted end-to-end success.
- Prefer a running service and available browser. Use a fresh browser context or otherwise restore a comparable starting state for each persona, without resetting a database or changing shared user data. If isolation is unavailable, run sequentially and document state carryover. Keep account and viewport requirements explicit.
- Give each agent its persona, assigned journeys, entry points, success criteria, account and environment context without credentials, permitted boundaries, evidence destination and reporting format. Avoid giving it other personas' findings before its first pass. Use real browser interaction and rendered states; a code review or a simulated description of clicks is not a browser run.

## Authenticated SaaS journeys

- Inspect available authenticated browser sessions and authorized test accounts first. Reuse an existing session when appropriate, or use the normal login flow with an account the user has authorized for the target environment. Identify the actual organization, workspace, subscription and role from the visible application where relevant; do not assume that a signed-in account has another role or access to another tenant.
- A fresh browser context is usually signed out. Before delegating, determine whether each persona can safely access a separate authenticated context using an approved mechanism. Do not copy, print, transmit or include passwords, API keys, session cookies, authentication state files or tokens in agent prompts, reports or evidence. If separate authorized sessions cannot be created, serialize access to the existing session and describe the shared-state limitation; never let agents concurrently control the same session. If login needs a user-held credential, MFA or consent, ask the user to complete it through the normal secure interface and continue only when access is available.
- Exercise the requested internal flow through visible navigation and controls: for example, open the relevant workspace or settings, find a feature, and reach its first meaningful outcome. Test only roles, organizations and subscription states actually available and authorized. Check relevant empty, loading, permission-denied or recovery states when they arise or can safely be reached; do not deliberately change roles, subscriptions or shared settings just to create a state.
- Check the consequences of actions before committing. Use explicitly authorized test data and an appropriate environment for state-changing flows; if creation, editing, deletion, invitation, payment, notification or other external effects are not authorized, stop before submission and mark the outcome unverified. Do not bypass authentication or permission checks, reset data, or assume cleanup is permitted. Do not log out, revoke a session or invalidate another person's work simply to isolate a persona.
- Keep public and authenticated findings distinct. For each persona record whether login was performed or an existing session was reused, the non-sensitive role and workspace context, the internal feature and success criterion, and any blocked step. A dashboard or successful login does not establish that an internal task succeeded.

## Ten simulated users

1. **Hurried**: skim the first screen, choose the first plausible primary action, and leave at the first error or blocker. Record whether first success was reached before leaving.
2. **Skeptical**: before registering, find and read pricing, terms, and privacy information; in an authenticated journey, look for the relevant plan, commitment, data-use or permission information before proceeding. Check whether the path back to the intended journey remains clear.
3. **Mobile**: use a 375 CSS-pixel-wide viewport, explore relevant controls by touch-like interaction where supported, and watch for overflow, obscured buttons and awkward wrapping. Report browser emulation separately from a physical device.
4. **Literal**: act only on what visible text and labels explicitly say; do not use hidden implementation knowledge or assume implied steps.
5. **Adversarial input**: try unusual, empty, boundary and malformed values, go back partway, and double-click relevant controls. Only use permitted non-destructive interactions and safe test data; do not duplicate a payment, send messages, or create irreversible records.
6. **First-time visitor**: arrive without prior product knowledge and look for what the service does, where to begin, and what information is required next; inside the product, approach the requested feature as a first-time user.
7. **Keyboard user**: navigate the relevant journey with keyboard controls, observing focus visibility, order, dialogs, and recovery. Do not claim screen-reader coverage unless actually performed.
8. **Returning visitor**: navigate away and back or use browser history during the journey, checking whether the user can understand and recover their place without assuming saved state.
9. **Language-switching visitor**: if localization exists and is in scope, change to an available alternate language and follow the journey, checking mixed languages, missing labels and clipped text. If no alternate language is available, record the language-switch check as not applicable and continue the journey in the available language. If a supported language cannot be selected because of an access or tool limitation, record that check as blocked and continue in an available language where possible. Record the journey outcome separately from the language-check outcome.
10. **Hesitant visitor**: compare available choices and look for cost, commitment, required information, cancellation or exit options before continuing; observe unclear choices or dead ends.

## Delegate and capture evidence

- When subagents are available and permitted, assign each persona as a separate task, retain the same entry and success definition for each shared journey, and collect independently observed results. Run in parallel only with genuinely separate browser contexts and safe, independent state; otherwise queue the tasks and run sequentially. Respect agent capacity and the browser tool's ownership rules. Never have multiple agents manipulate the same tab concurrently.
- Separate browser contexts do not isolate server-side records, account preferences or workspace settings. Before parallel work, identify whether personas share an account, workspace or mutable data. Run read-only work in parallel only when the environment supports it; serialize tasks that could interfere, and use separately authorized test data when available. If a prior run changes the starting state, record it and restore it only when restoration is authorized; otherwise report the resulting comparison limit.
- If delegation is unavailable or prohibited, perform the roles sequentially yourself using separate contexts where possible; report that these were sequential simulations, not independent agents. If real browser access is unavailable, report the blocker and do not claim a persona run or first success.
- At each meaningful confusion, blockage or apparent friction, capture a screenshot when permitted and safe; also capture the reached success or final blocked state. Record persona, viewport, starting state, URL without sensitive parameters, steps, expected and observed result, and screenshot path. Describe observable behavior and the likely user impact rather than asserting an agent actually felt frustrated.
- Store screenshots in a clearly identified local evidence directory with unique names by persona and phase; don't overwrite earlier evidence. Avoid capturing credentials, tokens, private data or unrelated account information. If a safe screenshot cannot be captured, document the reason and use a sanitized observation instead. Follow the environment's evidence retention and sharing rules.
- Stop at authorization boundaries and record the blocked step. Do not create accounts, transmit messages, make payments, modify production data or perform disruptive scans merely to complete a journey. User and project rules for database access, tests, builds and process starts take precedence.

## Consolidate, fix, and rerun

1. Collect every persona's report and group observations that have the same underlying problem. For each problem, record the personas affected, the number that encountered it, the number assigned to that journey who reached and could evaluate that step, and the total number assigned to and run on that journey. Separately identify personas blocked earlier, unable to evaluate the condition, or not applicable; do not count them as having passed the check. For example, if six of ten personas assigned to a journey reach a step and all six encounter the problem, report 6 affected / 6 evaluated, with 10 personas run and 4 not evaluated. Include severity, affected journey and step, screenshots and reproduction steps. Sort primarily by the number of affected personas, while flagging severe blockers and security or data-loss risks. Persona counts are heuristics, not population prevalence estimates.
2. If the user requested or otherwise authorized fixes, inspect the cause and fix the agreed in-scope issues as one coordinated change set, preserving unrelated work and the project's conventions. Do not start implementation for a review-only request. Report problems left unresolved and why.
3. After changes are available in the browser, rerun the same personas on their assigned journeys from comparable initial states with the same account role, workspace, viewport, entry point, success criterion and safe boundaries. Reuse or securely re-establish authentication as available; report differences in session or data state. Verify both each relevant original reproduction and whether the persona reaches first success; collect new evidence for any remaining friction. Do not assert a source change is live if the running service has not picked it up.
4. If a persona's initial or repeat run is blocked, state the journey, phase and reason; do not count it as passed. Report before/after results per persona and journey, problem counts, fixes and file locations, remaining issues, evidence paths, and any unperformed checks. Follow any prohibition on test or build execution; report when it prevents a requested recheck.
