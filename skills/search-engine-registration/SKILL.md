# 검색엔진 사이트 등록

구글·네이버·빙·다음의 사이트 등록과 소유권 인증을 지원한다. 사용자와 대상 프로젝트의 규칙을 우선한다. 스킬 추가·설치 요청만으로 실제 사이트 등록이나 계정 연결을 실행하지 않는다. 일반 SEO 개선, 광고, 분석 도구 추가는 별도 요청 범위다.

## 시작과 실행 범위

1. 사용자가 지정한 공개 사이트 URL, 대상 프로젝트, 요청 서비스와 작업 범위를 확인한다. HTTPS, www 유무, 경로, 리다이렉트 후 최종 주소를 구분하고 임의로 다른 사이트를 등록하지 않는다. 기존 등록 상태와 인증 코드·파일·메타데이터·robots.txt 생성 경로부터 살핀다.
2. 요청에 필요한 서비스의 아래 공식 문서와 현재 화면을 확인한다. 메뉴·지원 방식이 바뀌면 현재 공식 안내를 따른다. 도구가 없거나 로그인·접근이 막히면 준비 가능한 변경을 진행하고 남은 단계를 알린다.
3. 사용 가능한 연결 도구를 우선하고, 부족하면 허용된 브라우저를 사용한다. 기존 로그인 세션을 활용하되 대상 계정과 사이트를 확인한다. 비밀번호·MFA·CAPTCHA는 사용자에게 직접 입력하도록 맡긴다.
4. 코드 준비 요청이면 로컬 변경까지만 한다. 실제 등록까지 요청했다면 그 범위의 사이트 추가·인증 확인을 진행한다. 빙의 Google 계정 연결과 권한 동의가 이미 승인된 범위인지 확인하고, 미승인일 때는 표시된 권한과 대상 사이트를 구체적으로 제시한 뒤 해당 동의만 확인받는다. 이용약관 동의는 사용자에게 맡긴다. 반복 승인을 요구하지 않는다.

검토만 요청받으면 공식 공개 안내와 로컬 파일만 검토한다. 사이트 추가, 인증 값 발급·재발급, 인증 버튼 실행, 계정 연결, 이용 동의, 배포를 하지 않는다. 실제 등록에서는 서비스별 기존 상태를 먼저 확인하고, 현재 계정에서 대상 사이트의 유효한 인증과 필요한 권한을 확인했다면 재발급·코드 추가 없이 해당 단계를 완료로 기록한다. 공개 파일이 있다는 사실만으로 현재 계정의 소유확인을 추정하지 않는다. 구글 완료를 기다려야 하는 것은 빙 가져오기이며 네이버·다음은 독립적으로 진행할 수 있다.

## 공통 구현·확인 원칙

- 기존 프레임워크의 메타데이터 API, 정적 파일 제공 또는 robots.txt 생성 기능을 우선한다. 같은 URL을 만드는 파일과 동적 라우트를 중복 추가하지 않는다. 새 라이브러리·스크립트·API 자격증명은 이 작업에 기본적으로 필요하지 않다.
- 서비스가 현재 대상 계정과 사이트에 발급한 값만 사용한다. 값이 없으면 필요한 발급 단계와 적용 위치를 안내하고 가짜 값이나 플레이스홀더를 운영 코드에 넣지 않는다. 기존 다른 소유자의 인증 값은 임의로 제거하지 않는다. 인증용 HTML 파일은 발급된 파일명과 본문을 보존한다.
- `_KEY` 관련 값은 노출·전송하지 않는다(API 인증 용도 제외). 비밀번호, PIN, OAuth 토큰, 세션 정보를 출력·스크린샷·로그·완료 기록·커밋에 남기지 않는다. 공개 게시용 소유확인 문자열과 비공개 자격증명을 구분한다. 공개용 문자열이라도 `_KEY` 값 사용 제한과 충돌하면 게시하지 말고 대체 인증 방식 또는 사용자 직접 적용을 안내한다.
- DB는 조회만 허용하며 이 작업을 위해 DB 변경·초기화·리셋을 하지 않는다. 빌드·테스트는 임의 실행하지 않는다. 필요하면 사용자가 실행할 검증을 안내한다.
- 로컬 화면 확인은 실행 중인 프로세스를 우선하고 `localhost`를 사용한다. 없을 때만 프로젝트 규칙이 허용하는 범위에서 실행한다. 검색 서비스의 인증은 공개 사이트에서 이뤄지므로 로컬 확인만으로 인증 완료라 하지 않는다.
- 배포가 필요한 경우 실제 변경 파일과 내용을 먼저 준비한다. 기존 배포 승인이 있으면 그 범위에서 진행하고, 없으면 검토 가능한 변경을 제시한 뒤 배포 여부를 확인한다. 공개 사이트의 반영을 확인하기 전에는 인증 버튼을 반복 실행하지 않는다.
- 공개 URL은 비로그인 접근, HTTP 상태, 리다이렉트와 실제 응답 내용을 확인한다. 인증 파일이 SPA 대체 HTML을 반환하는 경우를 성공으로 처리하지 않는다. 메타태그는 홈페이지 응답의 `head`에 있는지 확인하고 클라이언트 실행 후 DOM 확인만으로 끝내지 않는다.
- 기존 `Disallow`, `Allow`, `Sitemap`과 비공개 경로의 차단 정책을 보존한다. 인증이나 검색 노출을 이유로 `Disallow: /`, `noindex`, 로그인 보호를 임의 해제하지 않는다. 필요한 변경은 별도 안내한다.
- 인증 실패 시 대상 계정·URL·발급 값의 일치, 공개 반영과 CDN 캐시, DNS·TLS 오류, 로그인·방화벽·봇 차단을 확인한다. 일반 브라우저 접근 성공만으로 검증 로봇의 접근까지 성공했다고 단정하지 않는다. 원인을 해결하거나 안내된 대기 시간이 지난 후에만 재시도하며 보안 설정을 임의 완화하지 않는다.

## 서비스별 절차

### 1. Google Search Console — URL 접두어

- [Search Console](https://search.google.com/search-console/)에서 기존 속성을 확인하고 필요한 경우 **URL 접두어**로 지정한 정확한 URL을 추가한다. 도메인 속성이나 DNS 인증으로 임의 전환하지 않는다. URL 접두어는 프로토콜·호스트·경로 범위가 다르면 별개다.
- 기존 상위 속성의 인증으로 URL 접두어 속성이 자동 인증되는 경우 추가 코드를 넣지 않는다. 그렇지 않으면 현재 제공되는 방식 중 기존 구조에 맞는 HTML 태그 또는 HTML 파일 등을 선택한다. 인증만을 위해 Analytics·Tag Manager를 새로 설치하지 않는다.
- HTML 태그는 속성 URL에서 비로그인 사용자가 최종 도착하는 페이지의 `head`에 둔다. HTML 파일은 인증 화면에 표시된 정확한 URL에서 직접 제공되도록 하고 리다이렉트 성공에 의존하지 않는다. 경로 접두어 속성도 파일 위치를 호스트 루트로 임의 추정하지 않는다.
- 공개 사이트 반영을 확인한 뒤 소유권 확인을 실행하고 결과를 확인한다. 인증 후에도 필요한 태그·파일을 유지한다.
- 공식 문서: [속성 추가와 URL 범위](https://support.google.com/webmasters/answer/34592?hl=ko), [소유권 확인](https://support.google.com/webmasters/answer/9008080?hl=ko).

### 2. 네이버 서치어드바이저

- [서치어드바이저](https://searchadvisor.naver.com/)의 웹마스터 도구에서 대상 사이트의 기존 등록과 소유확인 상태를 확인한다.
- HTML 파일 업로드 또는 HTML 태그 등 현재 지원하는 방식으로 발급된 값을 적용한다. 태그는 공개 홈페이지 `head`에 둔다. `body`, frame 내부, JavaScript·meta refresh·쿠키에 의존하는 이동을 소유확인 근거로 삼지 않는다.
- 공개 반영 후 소유확인을 실행하고 서비스가 표시한 성공·실패 결과를 기록한다.
- HTML 수정·파일 업로드가 불가능한 플랫폼은 지원 가능 여부부터 확인하고 우회 기능을 만들지 않는다. 인증 후 태그·파일을 유지한다. 공식 안내상 소유확인은 1년마다 필요하므로 현재 화면의 만료일·연장 가능 여부를 인계한다. 알림 설정 변경이나 자동 갱신 예약은 요청받은 경우에만 한다.
- 공식 문서: [사이트 등록 및 소유확인](https://searchadvisor.naver.com/guide/faq-start-register), [소유확인 가능 사이트](https://help.naver.com/service/30010/contents/17593?lang=ko&osType=PC), [소유확인과 주기](https://help.naver.com/service/30010/contents/17591?lang=ko&osType=PC), [기간 연장](https://help.naver.com/service/30010/contents/17603?lang=ko&osType=PC).

### 3. Bing Webmaster Tools — Search Console 가져오기

- [Bing Webmaster Tools](https://www.bing.com/webmasters/)에서 기존 사이트를 확인한다. 먼저 Google의 대상 속성 인증이 완료되어 있어야 한다.
- **빙 웹마스터 도구 화면에서** Google Search Console 가져오기를 선택한다. 승인된 계정 연결·권한 동의 후 표시된 사이트 중 요청된 사이트만 선택한다. 계정의 모든 사이트를 일괄 가져오지 않는다. 표시 URL이 정규화·그룹화되거나 기존 사이트의 권한 때문에 목록에서 빠질 수 있으므로, 대상이 보이지 않으면 기존 빙 등록 상태와 Google 권한을 대조한다. 비슷한 다른 사이트를 대신 선택하지 않는다.
- 가져오기는 사이트맵도 함께 가져오며, 이후 Google 접근을 통한 소유권 재확인과 새 사이트맵 자동 가져오기가 이어질 수 있음을 연결 전에 알린다. 이 동작이 사용자가 허용한 범위와 충돌하면 가져오기를 실행하지 말고 별도 인증 방식을 제안한다. 완료 보고에는 연동 유지 사실을 남기고, 접근 해제 시 재연결 또는 다른 인증이 필요할 수 있음을 안내한다. 연결을 임의로 해제하지 않는다.
- 가져오기 후 빙의 사이트 목록과 소유확인 결과를 확인한다. **구글 등록만으로 빙 등록까지 자동 완료되지는 않는다.** 가져오기 실행과 성공 확인이 필요하다.
- 실패하면 Google 속성·계정 권한·대상 URL·표시된 오류를 확인하고 원인 변경 없이 반복하지 않는다. 다른 인증 방식은 필요한 경우 별도 제안한다.
- 공식 문서: [사이트 추가·인증 및 Search Console 가져오기](https://www.bing.com/webmasters/help/add-and-verify-site-12184f8b), [빙 공식 가져오기 절차와 연동 유지](https://blogs.bing.com/webmaster/2019/9/Import-sites-from-Search-Console-to-Bing-Webmaster-Tools/).

### 4. 다음 웹마스터 도구 — robots.txt 인증

- [다음 웹마스터 도구](https://webmaster.daum.net/)에서 기존 URL·PIN으로 접근 가능한지 사용자가 확인하도록 한다. 유효한 기존 인증을 임의 재발급하지 않는다. 신규 발급이 필요하면 사이트 URL을 확인하고 PIN 입력·재입력과 이용 동의는 사용자가 직접 처리하도록 한다. 공식 도움말은 PIN 8~12자리와 동의 후 24개월 경과 시 재발급을 안내하므로 현재 화면에서 요구하는 조건과 유효 상태를 확인한다.
- **비공개 PIN 자체를 robots.txt에 적지 않는다.** 서비스가 robots.txt에 게시하도록 제공한 인증 문자열과 PIN을 구분한다. 인증 줄의 형식을 추측하거나 PIN에서 직접 생성하지 않는다.
- 현재 화면이 제공하는 게시용 인증 줄만 기존 루트 `/robots.txt`의 실제 생성 위치에 반영한다. 기존 크롤링 규칙을 보존하고 `_KEY` 관련 제한과 충돌하지 않는지 확인한다.
- 공개 `/robots.txt` 응답에 지정된 인증 줄이 있는지 확인한 뒤 현재 화면의 인증 절차를 완료한다. 발급 화면에 접근할 수 없으면 robots.txt 인증의 정확한 형식은 미확인으로 기록하고 임의 예시를 운영 코드에 추가하지 않는다.
- 공식 문서: [PIN 발급 절차](https://cs.daum.net/faq/service/15/category/4118/detail/38321). 이 도움말은 PIN 입력·동의·URL 인증키 발급을 안내하며, robots.txt에 넣을 정확한 줄은 실제 발급 화면에서 확인한다.

## 결과와 인계

- 서비스별 대상 URL, 수행 단계, 상태(준비 완료 / 공개 반영 대기 / 사용자 인증·동의 대기 / 소유확인 완료 / 실패 / 미확인), 확인 근거와 남은 작업을 보고한다. 인증 값이나 PIN은 결과에 복사하지 않는다.
- 코드 준비, 공개 반영, 서비스 소유확인 성공을 각각 구분한다. 사이트 등록·소유확인은 검색 수집·색인·노출 보장이 아니다.
- 별도의 사이트맵 제출·색인 요청은 요청받은 경우에만 기존 공개 사이트맵과 대상 URL을 확인해 수행하고 결과를 별도로 기록한다. 빙 가져오기에 수반되는 사이트맵 연동은 위 절차에 따라 사전 안내하고 결과를 구분한다. 인증 작업을 위해 사이트맵 기능을 새로 만들지 않는다.
- 변경한 파일마다 무엇이 달라졌는지 설명하고, 대상 프로젝트의 기존 문서 구조에 맞춰 당일 작업 완료 파일에 변경·확인·남은 단계를 기록한다. 기존 구조가 없다면 `docs/complete/YYYY-MM-DD-search-engine-registration.md`를 사용한다. 수행하지 않은 빌드·테스트·실제 등록을 완료로 기록하지 않는다.
